| Workflows | Deterministic graphs of typed nodes (mesa task 1607, replacing diagrams — the diagram tables were dropped and nothing migrated): `trigger`, `prompt`, `cli`, `script`, `branch`, `decide`, `output`, a DAG (`cycle` on a loop, at most one trigger, a branch's edges carry `true`/`false`, a decide node's carry an option or `fallback`, a `gate` node's (naru task 1993, a human approval polled in the db until `naru workflow gate approve|reject` or the API decides, a timeout rejecting) `approved` or `rejected` — `WorkflowEdge.branch` is a string). **The graph decides what runs, never an agent**: `core::workflow`'s engine runs a topological order (ties by node id), a branch activates only its matching edges, a `decide` node (mesa task 1655, `core::decide` called in-process: no process, network or key) only the edge of its chosen option when the confidence reaches its threshold and its `fallback` edge otherwise (none = everything downstream skipped, the run still succeeding; a decide error takes the fallback, or fails the node without one), a node none of whose incoming edges is active is `skipped`, and a failed node fails the run and skips the rest; a failed run is still a recorded run (`naru workflow run` exits 0 with `status` as data, the `script run` rule). The one model call is a `prompt` node's `llm::complete`: for `haiku`/`sonnet`/`opus` one synchronous `claude -p --output-format json` call through the eighth config template `workflow-prompt` (`claude -p … --tools "" --strict-mcp-config --output-format json`, **no API key**) run under the node's timeout, the answer being the result JSON's `result` (no polling, no stop, no transcript); for `local:<name>` Ollama's `/api/chat`; no tools offered; a script node's `{input}` values reach the script as arguments, never shell-parsed. The engine **never holds the store lock while a node's process runs** (`StoreAccess`). Names are unique case-insensitively across all workflows so the voice agent can run one by name (`naru-live` rule 15). **All routes carry `require_agent_access`, reads included** — a run executes shell. `serve --watch-workflows` (on by default; `=false` or `serve.watch-workflows: false` turns it off) runs due `time` triggers once per interval, the run row as the claim. The `ambient` trigger mode (`events` from `idea`/`can-help`/`wake`, mesa task 1643) fires on the ambient engine's events: `naru workflow emit` runs the matches synchronously, `POST /api/workflows/events` answers 202 and runs them in the background. `naru workflow defaults --project` (mesa task 1644, CLI only) creates two idempotent ambient workflows — label `idea` events into the `ambient` log, and a daily review filing one **backlog** task (an output node's `status` key, `backlog`|`todo`). **Every workflow keeps a version history** (naru task 2053, `workflow_revisions`, written by `Store` on every graph mutation: author `cli`/`web`, reason `edit`/`seed`/`restore of N`/`collapsed from <name>`, the whole graph as JSON; a burst of one author's edits folds into one revision): `naru workflow revisions|revision show|diff|restore`, `GET /api/workflows/{id}/revisions` + `POST .../revisions/{rev}/restore`, a History view in the builder; a restore keeps the workflow id, runs and node ids and adds a revision; **`defaults --builtins` reseeds a changed built-in in place as a `seed` revision — never a renamed copy, and `scripts/self-deploy.sh` renames nothing**; `naru workflow history collapse` folds old `(pre-…)`/`(copy)`/`(old)` copies into revisions after a db backup. **`KB: mine past sessions` and `KB: ongoing capture` are managed built-ins** (naru tasks 2103, 2118, `workflow_builtins` table, `Workflow.builtin`): `serve` installs/updates them on every start (global, reseeded in place), `Store` refuses every edit but enable/disable (`validation`, "duplicate it to customise"), a duplicate is an ordinary `(custom)` copy, and a pre-existing same-named user workflow is renamed `<name> (custom)` and kept; the kb-mine script inline in their cli node, created **disabled**, an install never touching any built-in's `enabled`; no built-in may reference a script outside the build (a unit test scans every node config); `naru workflow defaults --builtins` and the Workflows page's Install built-ins button (`POST /api/workflows/builtins/install`) run the same install. | `docs/workflows.md` |
| Inbox | The queue of things that need a *decision* and have no home yet (mesa task 1168): a `change-request` asking for work in some project, or an alert addressed to a person (`task-summary`, the cost guard's kind — never a task's close-out summary, whose record is the task's own `result`). Assigning converts to a task and **archives the item** as `converted-to-task`
with a `converted_task_id` pointer to the task it became (mesa task 1269 — before it, assign deleted the item, so that `archive_outcome` value was one nothing could write; a second assign of a converted item is `conflict`, and the bounded pointer stays in `--quiet`); archiving may carry an **`archive_reason`** (`mesa inbox archive <id> --reason "<why>"`, `POST .../archive {archived, reason?}`, ≤ 1000 chars, cleared by the un-archive, kept in `--quiet`) — the triage agent's verdict beside the item it decided. Every item **names the task it came from** — `task_id` is required at creation on both surfaces (unknown id = `validation`), the column is nullable only for pre-847 rows and is `ON DELETE SET NULL`, and the origin task's `task_name` + `project_name` ride back **derived on every read** (never stored) as the item's first line in the list (`inboxOrigin.ts`). There is therefore **no compose form**: the page triages, it does not author. Each item declares a **`kind`** — `task-summary` (an alert or report addressed to a person) or `change-request` (asks for work) — fixed at creation, defaulting to `task-summary` on both surfaces and for every pre-846 row, because an item nobody labelled must wait for a person rather than get an agent: the inbox-watcher triages **change requests only**, by two tool-less `claude -p --json-schema` calls in a detached `naru __job inbox-triage` (naru task 1691, `core::inbox_triage`: haiku decides, sonnet writes the task, Naru validates and applies the verdict through `Store`; the `inbox-triage` library agent is kept for manual use only — `docs/inbox-watcher.md`), and the web list tints each row by kind (`inboxKind.ts`) with the word in the meta line too. The page has three sub-views as tabs at its top (mesa task 1159; the nav's Inbox row is a single link) — **New** (`#/inbox`, unread), **Read** and **Archived** — a filter over the one polled list (`inboxFilter.ts`), never three fetches; an item the reader has open or is hearing stays on its view until closed, since both are what mark it read. **Archiving** (`archived_at`, `POST /api/inbox/{id}/archive`, `mesa inbox archive [--undo]`) sets an item aside without triaging or destroying it: it toggles (unlike `read_at`), outranks read state in every view and drops out of the unread badge. `project_id` FK is `ON DELETE SET NULL`, deliberately **not** `CASCADE` (as `task_id`'s is). A **play** button reads an item aloud through the naru-audio daemon — audio streams back to the browser *as it is rendered* (chunked, no `Content-Length`), the body reaches the daemon as the request body, in the voice `~/.mesa/config.json`'s `speech.voice` names; once it sounds, **rewind** and **pause/resume** drive that one `<audio>` without re-requesting the route, and rewind clamps to what is seekable because a chunked body has nothing earlier to go back to. The New view also reads its **whole queue**: one **read all aloud** button plays every unread item oldest first on a snapshot of ids taken at the press (`inboxQueue.ts`, never recomputed — playing an item is what marks it read), each later item reusing the element and clock that press unlocked, and the run ends on its last item, on any stop, on leaving the New view, and on a failure — while a row deleted out from under it counts as an item that ended, so the run moves on rather than wedging on it. There is **one player element for the page** and the press itself starts it (an autoplay policy weighs the gesture, not the render it schedules); a browser whose media stack refuses a range-less stream — Apple's does — re-fetches the same URL and **decodes the WAV itself**, scheduling each piece on a Web Audio clock the press unlocked, so it streams too; that mode is remembered for the page only, once decoded audio has actually sounded. Items list **collapsed** — a clamped plain-text preview a click expands — with the transport (symbols, not words) on the collapsed row and the triage controls only inside the opened item. An item is **unread** until `read_at` is stamped, which the *page* does — after the item has been held open a few seconds, or once it actually sounds — through an idempotent `POST /api/inbox/{id}/read`; the stamp is when it was **first** read, never moved and never cleared, and the nav badge counts unread items rather than all of them | `docs/inbox.md` |
| Naru live | A spoken conversation, living in the **header** (task 857): the person dictates into the capture box in the conversation sidebar the header opens, a dedicated Claude Code session answers, and every Naru reply is **spoken** back through the same naru-audio path the inbox uses (`speech::start`, chunked `audio/wav`, the Apple decode-it-yourself fallback, one `<audio>` per page, all unchanged — the only edit outside the feature is hoisting `playSpeechStream` from an inbox id to a **URL**). The loop is the *agent's*, and it **pulls**: `mesa live listen` → work → `mesa live say`, because the only channel into a live session is keystrokes over the attach PTY and the only way to read it is tailing a transcript, so Naru builds no second write path (same call `docs/agents.md`'s chat composer makes); since mesa task 1156 the agent runs `listen` in the **background** and ends its turn — at most one pending per lease, a new one started only in the turn the previous one's output arrived — and delegates long jobs isolated from project code (research, testing, investigation) to a fork (`Agent` tool, `subagent_type: fork`) or a specialized agent, the delegate told never to touch a `mesa live` command but one — its last step, `naru live result "<findings>"`, which the driver's next `listen` hands it as a `kind: result` record, surviving a handoff (mesa task 1359), no two of them in one tree, results delivered at a natural pause or at once when quiet, and neither the agent nor anything it spawns ever editing project code — a wanted change becomes a `backlog`/`todo` task — so the voice is never busy and a delegate finishing is heard at once rather than after a foreground wait. The queue is therefore two **tables** (`live_sessions`, `live_turns`, migration index 43), not server memory: the CLI opens its own `Store` and never talks to the server, so memory would be invisible to it — and `next_user_turn` is one `UPDATE … RETURNING`, so two listeners can never get one utterance twice. **At most one session is `live`** (a second `start` is `conflict`), which is why no command takes a session id — and why a **failed spawn ends the session it just opened** (`unavailable`, exit 1) rather than stranding one nothing is listening to that would `conflict` every retry. `GET /api/live` answers a ts-rs **`LiveState`** (`{session, turns, boards}` in `types.rs`), a view assembled per request and never stored, not an ad-hoc envelope. There is no routed page: the whole surface is `LiveHub`, rendered inside `<header>` beside the plan-limit chips — the header is mounted for the life of the app, which is what lets the conversation survive the very `navigate` turn it just performed (`#/live` survives only as a verb the hub intercepts to open its panel, hash put back). The **Naru waveform mark** — the favicon's seven bars, `components/NaruMark.tsx` painting `liveMark.ts`'s frames from one rAF loop (mesa task 1544, replacing the aperture canvas of tasks 874/973 and the head's text title) — sits in the panel head, no label, its accessible name `indicatorLabel`, and answers for **both** sides of the conversation in the same five ranked states (`liveIndicator.ts`, tasks 874, 882, 894): **hearing** (electric cyan, scale and bars following the **real** microphone level), **speaking** (warm amber/coral, following the **real** playback level — an `AnalyserNode` tapped off both playback paths, `speechTap.ts`, falling back to `simEnvelope` only if the `<audio>` element cannot be tapped), **working**/**resting** (the mockup's violet, no sound, a shimmer sweeping the bars), and **listening**/none (dim slate lavender, a slow breathe) with **paused** the same palette held still and dimmed — colour, scale and glow all eased, never snapped — speaking outranking the rest because the microphone is shut while she talks, paused outranking the three under it because a leftover draft is not the person still talking, hearing outranking working because words arriving are the stronger news and the agent carries on working either way, working outranking listening because listening is the resting state and work is not rest, and under `prefers-reduced-motion` every state keeping its motion at **half speed** rather than freezing (mesa task 1145 — reduce, not remove) — the clock halved inside `markFrame`, with the component subscribing to the query live so a setting flipped mid-session still takes effect with no reload; **working** is the session's own `working_since` (task 894), one nullable timestamp on `live_sessions` written by `Store::next_user_turn` — handing a turn over stamps it, a poll that finds nothing clears it, `end_live_session` clears it — and, for a pushed `run:<job>` agent, by the push's stamp, with the clear left to `Store::close_live_working` once the run is idle (naru task 2165, an empty `listen` poll no longer ending it) — so the span covers thinking, tool calls and file writes alike rather than only a request in flight (an agent that says "one moment" and then works stays lit), a session nobody has listened on reads as not working (`--no-agent`), and the page learns it on the `GET /api/live` poll it already makes rather than through anything new; since mesa task 1157 that poll also carries a derived, never-stored **`blocked`** (the agent's job's `waitingFor` off `claude agents --json --all`, cached 5s per job id, always null for a `run:<job>` agent — a `-p` session gets no permission prompt, a disallowed tool is denied rather than waited on — and null when `claude` is missing — and null too unless that `waitingFor` is present and names a **permission**, since `state: "blocked"` is one `requires_action` bucket whose other four reasons — `input needed`, `worker request`, `sandbox request`, `dialog open` — are not a prompt at all, mesa task 1293) and the page's own watchdog (`liveWatchdog.ts`, judged on every poll, always against one poll's own session-and-transcript pair) turns a **newly** blocked job (the rising edge of `blocked`, since the cached value outlives the span that answered the prompt) into a **notice turn**: a `naru` turn with `notice: permission` and a fixed sentence (and, naru task 1894, the derived `agent_ended` of a finished/failed/stopped/died run into an `agent-ended` one) (and, naru task 2015, a server-side hourly `cache-warm` notice written by `Store::add_live_warm_if_due` when no speaker is attached and the agent is idle) (a second kind, `stalled` — 30s of working silence — was removed by mesa task 1218 for firing on nearly every turn, migration index 63 clearing it from old rows), written by `Store::add_live_notice` through `mesa live notice` / `POST /api/live/notice`, deduped per working span, spoken once like any turn, labelled `notice` in the transcript and never indexed into the archive (`docs/live.md` "Telling the person the agent is stuck or silent"); on the desktop tiers the conversation and the whiteboard are two independent **dock panels** (mesa task 1567, `docs/dock.md` — LiveHub takes a `dock` prop in place of the slot, so a board push reveals the whiteboard panel and the three-way sidebar description that follows is the phone tier's); the conversation itself is a **right-hand sidebar** (task 887), a sibling of the agents one in `.shell-body`'s flex row so both can be open at once, either alone, or neither — Go live and Listen open it themselves (mesa task 1144), and on the desktop tiers its width is a drag handle on its left edge, remembered per browser in `localStorage` (`liveSidebarWidth.ts`, machine-local, double-click resets to the CSS `min()`), while the phone-tier drawer keeps its fixed width — only the rendered panel moved, portalled into a `.live-slot` div `App` renders just before `<AgentSidebar>` and handed down as a `slot` prop a ref callback sets, because everything that makes the hub work is anchored in the header (a fixed right-edge drawer on the phone tier, mirroring `.agent-sidebar`'s and sitting one `z-index` above it, since the conversation is the drawer holding the keyboard; the agents panel's width clamp subtracts the conversation's box — 0 while that box is `position: fixed`, the clamp being only-shrink — through a `ResizeObserver` keyed on the same `liveSlot` prop, because a portalled panel is not there to query on the first commit); it opens/closes without touching the session (closed = a zero-width clip, never `display:none`/`visibility:hidden`, so the capture box keeps focus and the dictation flowing into it); while live, joined and **unmuted**, the **page listens** (`liveRecognition.ts` for the gating rules, `liveAudio.ts`/`liveVad.ts` for the mechanism, mesa task 956, replacing the browser's own `SpeechRecognition`/`webkitSpeechRecognition`, task 873): the page opens the microphone through `getUserMedia`, runs it through an `AudioWorklet` loaded from a `blob:` URL, and a page-side voice-activity detector (`liveVad.ts` — onset/release hysteresis, a hangover that ends an utterance on a breath, a minimum length that discards a cough or a door, a maximum segment for a room that never falls quiet) decides where one utterance ends — landing exactly where the old recognizer's *final result* used to, so everything downstream (`heldWith`/`heldFlush`, both send boundaries, the mute switch, the pause) is unchanged. Each segment becomes a 16 kHz mono WAV (`liveAudio.ts`) posted to `POST /api/live/transcribe`, and the text the daemon returns is **held** as a recording, sent as **one** `user` turn once the person goes quiet for `live.auto-send-ms` or, sooner, when they press the listen switch (tasks 889, 917, 956). The two engines differ in exactly two observable ways, both gated on `path`: through the daemon, one-shot transcription has nothing to show mid-segment, so a "transcribing…" note stands in for the interim preview, and the silence clock moves only on **transcribed speech** — a segment coming back as words backdates `markHeard` to that segment's last loud frame, an empty one leaves it alone, and the flush is withheld while a segment is open or in flight (mesa task 1189, `speechHeardAt`/`shouldFlushSilence` in `liveRecognition.ts`); through the browser's own recognizer, the interim guess still feeds the send boundaries (though nothing displays it since task 1153) and `markHeard` fires on every `onresult`, interim included — the same question, "is the person still talking", answered by whatever signal that engine actually gives. A failed transcription does not end listening — the next segment tries again; a machine whose daemon is not ready never reaches this path, because which engine a page uses is decided once per conversation, at the moment it joins (`listenPath`, mesa task 957, `frontend/src/liveRecognition.ts`) from `GET /api/live/transcribe`'s `available` (the daemon's probe being `ready`, since mesa task 1389 the POST goes to the daemon; since mesa task 1388 it rides beside `state`/`engine`/`url`/`message`/`checked_at`, which on `naru-audio` report the daemon's TTL-cached `/health` probe — `docs/listen.md`; registered on the same route entry as the POST so a LAN page reads the same real answer a default-mode page does) — the daemon wins whenever it is ready, even where the browser has a recognizer of its own, and a page whose probe never answered falls back to that recognizer unchanged (task 873's original path, restored rather than replaced, `recognitionCtor`/`readResults`/`isBlockingError`/`SpeechRecognitionLike` back in use) or, lacking that too (Firefox, always), to the typed box. Which microphone feeds capture is a machine-local `<select>` in the panel's `.live-listen-row` above the capture box, beside the listen button — task 887 moved it out of the header cluster and changed nothing else about it, since which microphone and whether to use one are two settings on the same thing, read where the person decides whether to talk or type (`liveDevices.ts`, task 884, reworked by task 956), offered wherever there is more than one input (the old `MediaStreamTrack`-support probe is gone — a `deviceId` constraint is understood by every browser with `getUserMedia` at all); picking one opens `getUserMedia` with that `deviceId`, picking "Default mic" opens `getUserMedia` with no constraint — both now open a stream of Naru's own, unlike before task 956 — and the choice is remembered in `localStorage`, never sent to the agent or the server. Listening is **two** predicates, not one: `recognizesSpeech` (live + joined + capable of capturing audio + an open microphone + not paused + not muted) is whether the microphone is the way in, and `shouldListen` is that **minus the seconds Naru is speaking**, so she never hears her own reply — everything about the person's input method reads the first, only the capture stream's lifecycle reads the second, because Naru speaks for most of a conversation and a rule that blinks with playback is no rule. A `getUserMedia` refusal (`isMicRefusal`, `NotAllowedError`/`SecurityError`) is terminal for the page exactly as the old recognizer's refusal was; every other failure falls back to the default device, asked once. Segments transcribe **in order**, chained through a promise, so a late-resolving one never overtakes an earlier one; a segment in progress when the conversation ends, is paused or is muted is dropped rather than transcribed, since none of those is a recording that will be sent. **Nothing is sent while listening is on** except on one of its two boundaries (tasks 889, 917, 956): the transcribed segments pile up in a held recording (no longer displayed since mesa task 1153, which replaced task 1069's preview panel with a one-line status pill — `liveRecognition.ts::statusPill`, "Naru speaking" / "transcribing…" / "hearing" — at a reserved height above the capture box), and either the person going quiet for `live.auto-send-ms` (`shouldFlushSilence`, measured on `shouldListen` so the seconds Naru is talking are never read as the person falling silent, and restarted on every audible frame) or the press that turns listening off posts them as one turn (`heldFlush`) — since mesa task 1154 a segment still mid-capture or still in flight at that moment is transcribed first and folded in, the flush waiting behind it (`liveDrain.ts`). A VAD segment ends wherever the speaker drew breath, so a per-segment post made the agent answer a half-thought and then the rest of it; silence after the whole thought is the boundary the person meant, and the switch remains an explicit early send for whenever that wait would be wrong. A recording that would cross the server's 8 KiB `LIVE_TEXT_MAX` is flushed on a segment boundary and a fresh one begun, so a long monologue arrives as several ordered turns rather than one the server refuses — `heldFlush` being `heldWith` plus a trim. A **pause** keeps the recording already held (nothing already **held** is touched — pausing tears capture down the same way muting does, so a segment mid-capture at that moment is dropped rather than transcribed, but Resume carries the rest on) and the switch still sends while paused, since the recording belongs to the person, not to the moment they stepped out; **ending** the conversation clears it; and a refused microphone (`isMicRefusal`) flushes on its way out, `blocked` being what withdraws the only button that could have. The typed capture box is the fallback (muted, this browser unable to capture audio at all, or a refused microphone) and it **never takes the keyboard on its own** (mesa task 1439): it has focus only when the person clicks or Tabs into it, since a transcribed segment reaches the conversation with the keyboard anywhere and a grabbing box stole focus from the whiteboard, whose content box is `tabIndex={-1}` so a click there makes ⌘C copy board text. What the person **types** into that box is sent by **Enter alone** (mesa task 977) — except while speech is held, when it rides on the end of the recording's flush as one turn and Enter holds it for that flush rather than sending (mesa task 1351, `heldFlush`'s `typed`, `enterHoldsForRecording`); it used to auto-send after `live.auto-send-ms` of idle on the reasoning that dictation never presses Enter, but the box is the surface a person reaches for when they are typing, and a timer firing mid-sentence posts a half-thought — so that wait (task 886, edited in **Settings**, read once per conversation joined, clamped by the page) now governs only the *listening* surface's silence boundary above. Its controls are a **three-state** toggle (`liveSession.ts::liveControls`) — Go live / End / **Listen**+End, the last when a session is live but *this* browser has had no press (one started from the CLI, or a page reloaded mid-conversation); `Listen` used to call **no route**, existing purely to be the gesture an autoplay policy weighs; since mesa task 1267 it makes exactly one call — `POST /api/live/speaker`, the claim on the conversation's voice — and turns already heard are skipped by their server `played_at` so joining never replays from the top. That claim is the answer to two browsers open on one conversation both speaking every reply (`played_at` is stamped only once a turn has *finished* sounding, so it records what was said rather than claiming what is about to be, and the turns a page has taken in hand are its own React state): `live_sessions.speaker` names **one** client — an opaque id each browser generates once and keeps in `localStorage`, machine-local and never handed to the agent (`frontend/src/liveSpeaker.ts`) — claimed only by a deliberate press (Go live, Listen, unmute, Resume), newest press winning outright, while the page's ordinary route report carries the same id as a **refresh** that keeps a claim its client already holds and can never take one, so a background tab polling away never pulls the voice from the browser the person is talking to. `speaker` is **derived on every read** (`LIVE_SESSION_COLUMNS`): a claim unrefreshed for ten seconds reads back as `null`, judged in SQL on the **store's** clock (the `stale_claim_minutes` posture, never the browser's), so a closed tab frees the conversation rather than leaving it mute. The page's half is one pure predicate, `liveSpeaker.ts::maySpeak(speaker, client)` = `speaker === null || speaker === client`, both escape hatches folded into that first disjunct — an unclaimed conversation is speakable by every unlocked client, which is what Naru did before the claim existed and what an external client that knows nothing of the rule still does, and a stale claim arrives as `null` already — and `run()` gates the **speech** on it rather than the whole run, since a `navigate` is about what the person is looking at and every browser showing the conversation still follows it — which costs the page a **second set**, `performed` (`liveTurns.ts::actsOn`, "this page has already done what the turn does to the browser") beside `handled` ("this page took the turn in hand to **say** it"): one set for both put the turn a non-speaking page skipped into `handled` for ever with nothing to re-admit it, so a speaker killed mid-sentence — nothing stamping `played_at`, its claim going stale — left the freed page unable to say a turn it had already struck off, the exact silence the expiry exists to prevent. A page that may not speak therefore takes the turn in hand for **nothing** (`liveSpeaker.ts::takesToSpeak`, the one decision `handled` is written on) and walks the whole pending list rather than its head (`liveTurns.ts::pendingTurns`), performing each action once; a pure-action turn is unchanged, performed and stamped by every browser that reaches it. A fourth control, **Pause**/**Resume** (task 882), is offered only while live *and* joined and is likewise **route-free and browser-side**: the session stays `live` and the agent keeps working, while this page's run halts **whole** — nothing spoken, no `navigate`, no sidebar fold — the microphone shuts (`recognizesSpeech`, so the capture rules and hint see it) and the box disables, the transcript still accumulating and still readable; the sentence a pause cuts off is **replayed from its start** on Resume (mesa task 1161: `pauseNow` hands the sounding turn back out of `handled` through `liveTurns.ts::releaseForReplay` before `silence()`, since a turn is taken in hand before it sounds and stamped only when it ends — `End` releases nothing, its transcript resets anyway), then everything that piled up is caught up in transcript order with no new gesture (`unlocked` was never given up), and ending a conversation clears the pause.
