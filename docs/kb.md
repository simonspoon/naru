# Knowledge base (`naru kb`)

A small personal knowledge base of markdown notes, filed by a model and
answered from by a model, where **Naru does every write and every check**
(naru task 1919). CLI first; a read-only web viewer (below) sits over the same functions.

```
naru kb add [--source <label>] [--session <id>] <text…> | --file <path> | --stdin
naru kb ask <question…>
naru kb list [--topic <topic>] [--session <id>]
naru kb show <path>
naru kb usage [--days N]
naru kb hook            # run by the kb-lookup.sh hook, reads a payload on stdin
```

## Layout

Under `<naru home>/kb/` (`~/.naru/kb`, or `~/.mesa/kb` on an install that
predates the rename; `NARU_KB_DIR` / `MESA_KB_DIR` overrides it):

| Path | What |
| --- | --- |
| `topics/<topic>/<slug>.md` | a note. `topic` and `slug` match `[a-z0-9][a-z0-9-]{0,39}`; at most 50 topics; a note body at most 16 KiB. Front matter (`title`, `tags`, optional `sessions`, `updated`) then the markdown body |
| `INDEX.md` | one line per note, `topics/t/s.md \| title \| tags \| updated`, **regenerated by Naru from the files** after every apply — never edited by a model |
| `log.jsonl` | append-only `{ts, op: create\|append, path, bytes, source}`, one `O_APPEND` write per line |
| `spool/<id>.md` | the raw text of a queued add, removed only when its job succeeds with no refused op; **kept** when the call fails or any op is `failed` (the report then carries `spool`, its path) |
| `.lock` | the `flock` that serialises applies |
| `lookups.jsonl` | one line per automatic lookup (below) |
| `lookups-seen/<session id>` | an empty marker: that session has had its one lookup |

## `kb add`

The text (words, `--file` or `--stdin`, exactly one; non-empty, at most 32 KiB)
is spooled and a detached `naru __job kb-add` is started. **The add is
asynchronous**: the command prints `{"id": "<spool id>", "status": "queued"}`
and returns; the notes exist once the job finishes, and its one-line JSON
report (`applied`, `failed`, `dropped`) or its error goes to
`logs/kb.log`. A job that cannot start is `unavailable` and nothing is queued.

The job makes one tool-less `claude -p --output-format json --json-schema`
call per 12 KiB chunk of the text through the **`kb` config template**
(`docs/config.md`; model `haiku`, no API key, cwd `~/.naru/workspace`). The
prompt carries the raw text and the current index inside `<<<DATA … DATA>>>`
fences; the answer is `{ops: [{op, topic, slug, title, tags, body}]}`, at most
5 per call. **The model never touches a file.** For every op Naru:

- checks `topic`/`slug` against the pattern, builds the path itself, refuses a
  symlink at `topics/`, the topic folder or the note, and checks the canonical
  path stays under the canonical kb root;
- requires `create` to be a new note (else `conflict`) and `append` an existing
  one, an empty body, the 16 KiB cap and the 50-topic cap;
- writes the file atomically and logs it, all under the `flock`, then rebuilds
  `INDEX.md`.

### Source sessions (naru task 2575)

Each note records the Claude Code sessions it was filed from, so notes from
one session can be found together. `--session <id>` (1-64 of
`[A-Za-z0-9_-]`, else `validation`) defaults to `CLAUDE_CODE_SESSION_ID`
when that is set and well formed, else no session. The id rides the job's
`--session` argument, and every note the add creates or appends to gets it
in a `sessions: a, b` front-matter line between `tags` and `updated`:
deduplicated (a repeat moves to the end), the most recent last, at most the
last 20. An append without a session keeps the list; `kb merge` appends the
drops' sessions after the kept note's (kept first, then each drop's in order). A note with no session has no
`sessions:` line, and a note written before the field reads as an empty
list. `INDEX.md` and the prompts do not carry it.

### Backfilling sessions from the log (naru task 2577)

`naru kb backfill-sessions` gives notes filed before the field the sessions
`log.jsonl` records for them. It is a dry run unless `--apply`, and prints
`{applied, notes, notes_updated, notes_without_sessions, rows_mined,
rows_skipped_missing_path, rows_skipped_unresolved_merge,
rows_skipped_no_front_matter}` (row counts are `mined-session-<id>` rows).

- Rows are read in `ts` order (ties keep file order). Each `create`/`append`
  whose source is `mined-session-<id>` adds `<id>` to the note at `path`,
  with the same dedupe and last-20 cap as above.
- A `kb merge` writes a `merge` row for the kept note, then a `delete` row
  per drop. Each such `delete` moves the dropped note's sessions to that
  kept note, the way `kb merge` unions them. Any other delete loses them
  (`rows_skipped_unresolved_merge`). The log has no rename op, so a note
  moved by hand is not followed: its rows count as
  `rows_skipped_missing_path`, like rows for any note that no longer exists.
- Sessions a note already records go after the backfilled ones. Only the
  `sessions:` line is rewritten (placed before `updated:`); body, title,
  tags and `updated` stay byte for byte, and a file without Naru's front
  matter is skipped (`rows_skipped_no_front_matter`). `INDEX.md` holds no
  sessions, so it is never rebuilt. A second run changes nothing.

On a copy of the real kb (2026-11-04: 1336 notes, 2020 log rows) it updated
1311 notes. 25 notes stayed without sessions: the 10 filed with no mined
session, plus 15 whose 25 rows point at paths moved to another topic outside
the log.

Each op is judged alone: a refused one is listed under `failed` in the report
and the rest still land. Any refused op keeps the spool file (its path is in
the report's `spool` key in `logs/kb.log`), so the text can be re-filed.

## `kb ask`

Synchronous. A keyword prefilter (below) picks up to 8 notes; one haiku call
gets the question, the index and those notes and must answer **from them
only**. Naru then drops every cited source that is not one of the notes
actually shown to the model. Outcomes:

- an empty kb, no keyword hit, or a model that says the notes do not answer:
  `{"answer": "", "sources": []}`, exit 0 (the first two make no model call);
- an answer with at least one real source: `{"answer", "sources": [{"path", "title"}]}`;
- an answer citing no real note, or a failed call, or a missing `claude`:
  `unavailable` (exit 1).

The prefilter stems each question word crudely (one of `ing`/`ed`/`es`/`s` off,
never below 4 letters) so "dumps" finds "dump", and offers the model up to 8
notes. It is the lookup's IDF-weighted prefilter (below), each word's weight
raised by 1 so a word in every note of a tiny kb still finds it. Since naru
task 2662 it keeps two-letter words (`rm`, `cp`, `ls`; a short stop list drops
`do`, `in`, `is` and the like) and matches them as whole words, so `rm` does
not hit "form" or "permission"; before, such words were dropped and a question
like "rm -rf" asked nothing. Hits are capped as below (the old `kb ask` capped
only the body, at 10). The prompt tells the model to combine notes for a
multi-note question and to treat a nearby-but-different fact as no answer.

Measured for naru task 2662 on a copy of the real kb (1,371 notes, real
haiku), with 26 questions whose answering notes are known (short and
symbol-heavy ones such as `rm -rf`, `exit 137`, `ls eza`, `jq regex s flag`,
plus folder trust, BlackHole testing and naru-audio rm-before-cp):

| | before | after |
| --- | --- | --- |
| `kb ask`, right note cited | 23 / 26 | 24 / 26 |
| lookup (`kb hook`), right note cited | 24 / 26 | 26 / 26 |
| `kb ask` latency avg / max | 3.9 / 6.4 s | 4.4 / 8.9 s |
| lookup latency avg / max | 4.7 / 6.7 s | 5.3 / 8.4 s |
| lookup replay (90 real titles): injected | 36 (40 %) | 41 (45.6 %) |
| replay: relevant / misleading / failed | 94.4 % / 2 / 1 | 92.7 % / 3 / 0 |
| replay latency p50 / p95 | 6.2 / 11.8 s | 6.2 / 9.2 s |
| `scripts/kb-eval.sh` (fictional, 41) | 41 | 41 |

No question answered before went unanswered after, in either set. The two
`kb ask` misses left are `rm -rf` and "how do I safely rm -rf a directory held
in a shell variable?". Before, the first made no model call, and the second
showed the model eight notes without the rm one. Both now show the rm-hook note
first, and the strict prompt judges it nearby-but-different. The lookup
answers both.

### Session siblings (naru task 2576)

After either prefilter (`kb ask`'s or the lookup's below) picks its notes,
up to `SIBLINGS` (2, `src/core/kb.rs`; 0 turns it off) notes that share a
source session (`sessions:`, above) with one of the first `SIBLING_SEEDS` (3)
picks and are not already picked join them, right after those three, so the
byte budget still cuts the weakest keyword hits first. The total stays at 8:
a sibling displaces the last hit. Seeds are taken best first, each one's
sessions most recent first, each session's notes by path; a sibling may be
cited like any other shown note. No keyword hit still means no call, and a
note without sessions brings no siblings, so on a kb filed before task 2575
this does nothing.

Measured with `scripts/kb-lookup-replay.sh` (90 real lookup titles, real
haiku, sonnet judge) on a copy of the real kb whose notes had their sessions
backfilled from `log.jsonl`'s `mined-session-<id>` sources (1,311 of 1,336
notes), two runs off against one on:

| | off | off (repeat) | on |
| --- | --- | --- | --- |
| injected | 26 (28.9 %) | 24 (26.7 %) | 24 (26.7 %) |
| relevant (judged) | 96.2 % | 100 % | 100 % |
| misleading | 0 | 0 | 0 |
| failed | 0 | 2 | 0 |
| latency p50 / p95 | 7.6 / 12.6 s | 7.6 / 12.2 s | 7.4 / 12.4 s |

Siblings reached 84 of the 88 prompts that had notes (1.8 each). They were
cited in 3 injections, all judged relevant, while the off runs cited a hit
they displaced in 4 questions, and no question both off runs injected went
empty with them on: not worse, within haiku's run-to-run noise, so it
ships on. Most added siblings were off-topic for the task, which the
`fit` gate absorbs.

## Evaluating `kb ask` (naru task 1944)

`scripts/kb-eval.sh [label]` seeds `scripts/kb-eval/facts/` (25 fictional notes,
so the model cannot know them) into a **throwaway** `NARU_KB_DIR` / `NARU_DB`
under a temp dir (never the real kb), runs the real `naru kb ask` (real `claude`
haiku, ~41 calls, 4 in parallel) over `scripts/kb-eval/questions.json` and
scores deterministically: positive questions need every `all` regex in the
answer, no `none` regex, and a cited source from the expected list; a negative
question is correct only if the answer is empty (or an explicit "not stated"
without any forbidden fact). It prints a per-type table and the failing
questions (got vs why) and writes `<out>/<label>.json`. Env: `NARU_BIN`
(default `target/release/naru`, rebuild after changing `kb.rs`), `EVAL_OUT`,
`EVAL_JOBS`. Not part of any gate.

Before/after the prefilter stemming + 8 notes + prompt change (41 questions;
haiku is not fully deterministic, a second after-run was identical):

| type | n | before | after |
| --- | --- | --- | --- |
| direct | 10 | 10 (100%) | 10 (100%) |
| multi-hop | 9 | 7 (78%) | 9 (100%) |
| paraphrased | 12 | 11 (92%) | 12 (100%) |
| negative | 10 | 9 (90%) | 10 (100%) |
| all | 41 | 37 (90.2%) | 41 (100%) |

Average latency was 3.3 s before and 3.2-3.4 s after. The fixture is small and
the questions were written before tuning, so 100% means these failures are
fixed, not that `ask` is perfect: a bigger or noisier kb, or a paraphrase
sharing no word with its note, still misses at the prefilter.

## Automatic lookup (naru task 2274)

Notes were being filed but never read back, so the `kb-lookup.sh` library
built-in (`core::kb_lookup::KB_LOOKUP_HOOK`) asks the kb at the start of
**every** Claude Code session. Enable it once per machine:

```
naru library hook enable kb-lookup.sh --event UserPromptSubmit
```

The script only pipes Claude Code's payload into `naru kb hook`, which:

- looks up only the **first** prompt of a session (an `O_EXCL` marker in
  `lookups-seen/`, claimed before the call; a resumed session keeps its id, so
  it is not asked again, and a failed or timed-out lookup is not retried);
- asks with the prompt — only its first non-empty line when it runs over 40
  words — or for a queued `/execute-naru-task N` (or `execute naru task: N`)
  with task N's title, the first non-empty line of its description (an
  unknown task asks nothing). Only the title, because the prefilter takes
  every word of the question: asked with whole task texts, generic words
  (`naru`, `audio`, `test`) picked the notes and 98 of 100 lookups came back
  empty (naru task 2409);
- runs the **lookup** (`kb::lookup_with`, naru task 2553), not the ordinary
  `kb ask`: the strict ask prompt ("answer only what was asked") returned
  empty for task titles, so 0 of 246 lookups injected anything. The lookup
  differs from `kb ask` in three ways (naru task 2662 gave `kb ask` the same
  prefilter, each weight raised by 1, so there only the weights differ):
  - an **IDF-weighted prefilter**: each keyword scores
    `ln((N+1)/(df+1)) x (3 x min(title/tags/path hits, 2) + min(body hits, 3))`,
    `df` being how many of the `N` notes hold it as a (crudely stemmed) word,
    hits counted as substrings (a two-letter word's as whole words), top 8
    kept (2 of them may be session siblings, above) — so words in
    most notes (`agent`, `naru`, `panel`) stop picking the notes. A word in
    every note scores 0, so a one- or two-note kb rarely injects anything;
  - a **task-framed prompt** (`LOOKUP_PROMPT`, no index): the facts from the
    notes that bear on starting this task, at most ~40 words, a note about
    the same component, tool or problem counting;
  - a **relevance gate**: the answer carries `fit` (`strong|weak`, schema
    `LOOKUP_SCHEMA`), `strong` only when a note is about the very component,
    feature, file or tool the task changes or names a pitfall it will hit.
    A `weak` fit is answered empty. On the 90-title benchmark the gate cut
    the ungated lookup's 58 injections to 46 and its 14 judged false
    positives to about 6;

  one haiku call through the `kb` template, handed what is left of a **15 s**
  budget (a typical lookup takes 7-8 s; 6 s before task 2553) and killed at
  it. The steps before it (opening the db, reading the notes) are not under
  the cap — about 0.25 s on a 1,000-note kb, though a locked db can add up to
  its 5 s busy timeout;
- when the answer cites real notes, prints the hook's `additionalContext`: the
  answer cut to 150 words, the cited note paths and titles (however short
  the answer), and how to read one —
  framed as data from earlier sessions, not instructions. No answer, no
  keyword hit, an error or the timeout inject nothing; it always exits 0, so a
  prompt is never blocked;
- appends one `lookups.jsonl` row: `ts`, `unix`, `session_id`, `cwd`,
  `project` (the folder's project name, `null` when none), `transcript_path`,
  `question`, `sources`, `latency_ms`, `injected`, `outcome`
  (`injected|empty|failed`) and `error`. An empty kb is not looked up or logged.

It **never fires** — nothing asked, nothing logged — when `NARU_KB_SKIP` is set,
which Naru sets on every `claude -p` call it makes itself (`llm.rs`: the kb's own
ask/add calls, so a lookup cannot recurse, plus triage, retro, live memory and
workflow prompt nodes) and on every workflow `cli`/`foreach`/`verify` node (so
the `KB: ongoing capture` / `mine past sessions` runs and anything they start
are skipped); for a session whose `cwd` is under Naru's workspace
(`~/.naru/workspace`, where every Naru job and `kb-mine.sh`'s calls run); and
for a **`naru-live`** driver, whose one prompt is the `Drive naru live session
…` boilerplate (its real turns arrive through `naru live listen`, never as
prompts, so a lookup there would only ever be noise).

### Replaying the automatic lookup

`scripts/kb-lookup-replay.sh [label]` copies the real kb's notes into a
throwaway kb (`NARU_KB_DIR`, plus a throwaway `NARU_DB`; the real kb is only
read), replays the last `REPLAY_N` (default 90) distinct `lookups.jsonl`
questions through the real `naru kb hook` (real haiku), then a strict blind
judge (sonnet, one call per injection) scores each injection 0-3 and flags
misleading ones. It prints `{questions, injected, injected_pct, failed,
failed_pct, latency_ms_p50/p95/max, judged, misleading, relevant_all_pct,
sample, relevant_sample_pct}` (`relevant` = score 2-3 and not misleading;
the sample is a seeded 30) and writes every lookup and verdict to
`<EVAL_OUT>/<label>.json`. Env: `NARU_BIN`, `KB_SRC`, `REPLAY_N`,
`REPLAY_JOBS` (default 6), `EVAL_OUT`. Task 2553's targets: injected at least
30 %, at least 70 % of the sample relevant, fewer misleading than the ungated
14 of 90, p95 under the 15 s cap, under 3 % failed.

### `kb usage`

`naru kb usage [--days 28]` reads `lookups.jsonl` and, for each injected
lookup, the session's transcript: it counts as `useful` when an **assistant**
line (text or tool call) names a returned note's path, its `topic/slug`, or its
title when that is 16+ characters — the injected context itself is not an
assistant line, so it never counts. Otherwise `unused`, or `unchecked` when the
transcript is gone. Prints `{lookups, useful, unused, unchecked, empty, failed,
avg_latency_ms, days, weeks: [{week, …same counts}]}`, `week` being the UTC
Monday. The heuristic misses an agent that uses a fact without naming its note.

## `kb list` / `kb show`

`list` prints a bare array of `{path, topic, title, tags, updated, sessions}`;
`--session <id>` keeps only the notes whose `sessions` hold that id (with
`--topic`, both must match). `show` prints `{path, body, sessions}`; a path
that is not a note in the kb (outside it, malformed, a symlink, absent) is
`not_found`. `--quiet` on `show` drops `body`;
`list`, `ask` and `add` accept and ignore it.

## `kb dupes` / `kb merge` (naru task 2277)

`kb dupes` is read-only: it prints clusters of near-duplicate notes as
`[{score, notes: [{path, title, tags}]}]`, biggest first (`--quiet` drops the
tags; paths stay, so they feed `kb show` and `kb merge`). No model call: each
pair scores 0.7 x the Jaccard overlap of the title+body words (lowercased,
stop words and words under 3 letters dropped, crudely stemmed) + 0.15 x the
title-word overlap + 0.15 x the tag overlap. Pairs at or above the threshold
(default 0.3, `--threshold` to change) are joined into clusters (connected
components); `score` is the mean of a cluster's pair scores. On the real kb
(~1000 notes) 0.3 gave 35 clusters, the largest 6; 0.2 chains unrelated notes
into one 145-note cluster.

`kb merge <keep> <drop>...` keeps `<keep>` and appends to it each paragraph or
bullet line of the drops it lacks (whitespace- and case-insensitive compare),
unions the tags (the usual cap of 8), then deletes the drops, logs a `merge`
and a `delete` line per note in `log.jsonl` and rebuilds `INDEX.md`. Prints
`{kept, removed}`. Everything is checked first: an unknown or malformed path is
`not_found`, a keep listed among the drops, no drops, or a merged body over the
note cap is `validation`, and nothing is written. `kb ask` reads the files, so
it never cites a removed note. A drop's title and `updated` are discarded, and
the merged tags are capped at 8. `--threshold` must be above 0 and at most 1.

## Web page (`#/kb`, naru task 1928)

A nav entry "Knowledge base" opens `#/kb`: an Ask box over
`POST /api/kb/ask` showing exactly what `naru kb ask` returns — the answer, the
sources (path + title, each linked to `#/kb/<note path>`, which shows that
note's source sessions — each linked to `#/cc/sessions/<id>` — its markdown
and a back link), an empty-result state and the raw
JSON in a collapsed block, plus the front page below
(`frontend/src/kbFilter.ts` keeps only the route helpers). No new storage;
thin routes over `core::kb`, all `require_agent_access` (ask spawns
`claude`):

- `GET /api/kb/notes[?topic=&session=]` — as `kb list` (metadata only)
- `GET /api/kb/note?path=topics/t/s.md` — as `kb show` (`not_found` outside the kb)
- `POST /api/kb/ask {"question"}` — as `kb ask` (JSON Content-Type required)

### Front page (naru task 2552)

Around the Ask box `#/kb` shows, all derived in `frontend/src/kbFront.ts`
(pure, unit-tested) from the routes below:

- **Stats row**: total notes, notes whose `updated` is within the last 7 days,
  and the automatic lookup's hit rate — `useful + unused + unchecked` over
  `lookups` from `kb usage` (28 days); `—` with no lookups.
- **Topic bubble map**: one SVG circle per topic, area proportional to its note
  count (a floor radius keeps a one-note topic clickable), coloured by its
  newest note's age (this week / month / 3 months / older, theme variables).
  Labels show only where they fit; a chip row below names every topic. Picking
  a bubble or chip lists that topic's notes (title, tags, updated, newest
  first), each linking to `#/kb/<path>`.
- **Recent notes**: the ten newest by `updated`.
- **Duplicates to merge**: `kb dupes` clusters, a radio to pick the note to
  keep (the first by default), and a Merge button that asks to confirm before
  running `kb merge`; the clusters and notes are refetched after.

Routes added for it, same `require_agent_access` boundary:

- `GET /api/kb/usage[?days=]` — as `kb usage` (default 28)
- `GET /api/kb/dupes[?threshold=]` — as `kb dupes` (default 0.3; out of range is `validation`)
- `POST /api/kb/merge {"keep", "drop": [..]}` — as `kb merge` (JSON Content-Type required)

## Mining past sessions (a workflow, not a feature)

The saved workflow `KB: mine past sessions` (voice trigger "mine sessions into
the knowledge base"; `workflow run <id> --input N` reads N sessions, default 2,
max 5) is a trigger, a `cli` node running `~/.naru/bin/kb-mine.sh` and a log
node. The script, which lives outside the repo, picks the newest unprocessed
sessions from `cc sessions` (8+ messages, ended 20+ minutes ago, not Naru's own
workspace jobs), has haiku extract only gotchas and new facts from `cc chat`
(transcript fenced as data), drops each fact `kb ask` already answers, files the
rest with one `kb add --session <that session id>`, and appends the session id to `~/.naru/kb-mined.txt` so
it is never read twice.

**Ongoing capture** (naru task 1951): the saved workflow `KB: ongoing capture` is the
same trigger → `kb-mine.sh` → log chain on a `time` trigger (every 60 minutes, so
`serve --watch-workflows` runs it unattended, 2 sessions per run). It shares the
`~/.naru/kb-mined.txt` ledger, so a session is never mined twice by either
workflow. Disable it with `naru workflow update "KB: ongoing capture" --enabled false`.

## Not covered

`naru migrate` does not carry the kb: move `<naru home>/kb/` by hand. The kb
is not a project notebook (`docs/project-memory.md`); the only hook that reads
it is the opt-in `kb-lookup.sh` above.

Gate: `scripts/kb-check.sh`.
